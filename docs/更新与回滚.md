# 安装、更新与回滚

本页说明候选源码中安装工具的边界，不是部署或运行时验收记录。2026-10-30 的 0.2.2 试装已撤回；本轮只硬化源码工具，**0.2.2 仍是待原生运行时验证的候选**，实装版本以对应部署记录为准。源码检查、文件写入成功、桌面启动和外部模型行为分别留证，不能互相代替。原暂停演练及 H1/H2/H3 的用户批准边界不因维护变化。

## 先只读核验，再关闭桌面操作

1. 保留旧版、候选源码和独立备份，先完成适用的软件检查。
2. 用 `-CheckOnly` 读取源码、目标目录、profile、依赖声明和桌面状态。预检可以在 DSH 开启时运行，不改插件、profile、锁文件或依赖。
3. 实际安装、更新或恢复前，保存工作并正常退出 DSH。脚本不会强制关闭进程，不允许活跃 Host 下换文件；写入前会再次核验桌面已退出。
4. 更新和恢复只处理当前用户 `.dsh/plugins/dsh-mcm-team` 这一标准目录，以及该用户 `.dsh/profiles` 下的命名 profile。`-PluginRoot` 不能绕过路径检查；非常规布局先只读确认，再制定单独迁移方案。

命令中的 CLI 和备份路径均为占位符，须替换为本机实际路径。收据及 profile 备份留在仓库外，不公开用户的真实备份路径。

```powershell
pwsh -File tools/update-dsh.ps1 -DshCli '<实际 dsh.cmd 路径>' -CheckOnly
pwsh -File tools/update-dsh.ps1 -DshCli '<实际 dsh.cmd 路径>'
```

可选 `-Profile`（默认 `desktop`）、`-BackupRoot`。路径相交、重解析点及实际链接目标均须通过工具检查；仅有相同字节的普通目录副本不能冒充已登记链接。

## 已登记标准链接的更新

标准更新要求 profile 已登记 MCM，且该 profile 的 MCM 包确实通过 junction 或 symlink 指向标准插件目录。工具读取实际链接及其目标，不能只根据 manifest 的 `link:` 字符串或文件相同就判定成功。

更新前比较旧插件与候选的依赖合同：`dependencies`、`devDependencies`、`optionalDependencies`、`peerDependencies`、`peerDependenciesMeta`、打包依赖和 `engines` 等声明须一致。相同时，工具先备份并校验完整插件树与相关 profile 状态，再暂存候选并通过目录换入更新 MCM 文件；**不调用 DSH CLI，不重写 profile 或锁文件，不改共享 `node_modules`**。非 MCM 包配置和已保存状态继续核验。

依赖合同变化时以 `MCM_DEPENDENCY_MIGRATION_REQUIRED` 拒绝。此时需另立迁移计划，明确依赖求解范围、备份及恢复方法；不能把迁移伪装成文件更新，也不自动补锁、禁用其他插件或改凭据。

新更新收据使用 v3：

- `install_mode: registered_link_file_swap`
- `dependency_install_performed: false`
- `status: installed_pending_runtime_verification`

这些字段证明工具采取的文件操作范围，不表示新版本已通过真实运行时或模型行为验收。工具保留旧插件备份及换入前后哈希；不要删除备份或仅凭版本号判定状态。

## 锁文件预检能证明什么

`-CheckOnly` 对 profile 根锁文件的 importer 和直接依赖 specifier 做只读核对，输出 `consistent`、`mismatch` 或 `unknown`。检查器使用 Python 3 标准库，无第三方 YAML 依赖；仅支持 pnpm 9 规范 block importer 的明确子集，不支持的语法或无法确定的输入记为 `unknown`。这是直接声明审计，**不是 pnpm 完整锁文件验证**，也不证明所有传递依赖和运行时文件正确。

`mismatch` 或 `unknown` 会明确警告。对于已经登记真实标准链接且依赖合同相同的文件更新，可以继续，因为该路径不运行依赖安装，不改变共享依赖。警告仍须保留，文件更新不会修复锁文件，也不能把原有异常写成一致。

首次安装需要官方 CLI 改动依赖：若已有 profile 的根锁文件审计为 `mismatch` 或 `unknown`，入口会在调用 CLI 前拒绝。新建空 profile 没有既有锁文件时按首次安装处理，不伪报为已有锁文件一致。

## 首次安装

```powershell
pwsh -File tools/install-dsh.ps1 -DshCli '<实际 dsh.cmd 路径>' -CheckOnly
pwsh -File tools/install-dsh.ps1 -DshCli '<实际 dsh.cmd 路径>'
```

首次安装仍使用官方 CLI 链接本包 `bundle` 目录，请保持源码路径稳定。检测到已登记的标准安装时转入上述文件更新路径。首次安装的源码链接不自动迁移成标准目录；已登记但标准目录或链接状态不符时拒绝覆盖，先核实实际布局。

首次安装可能让 CLI 创建或更新 profile 依赖，不能把它描述为文件替换。首次安装失败也不代表已有可回滚收据；保留现场，检查 CLI 实际结果，不套用另一台机器或另一 profile 的备份。

## 回滚只恢复已证明可独立恢复的 MCM 文件

先使用本次操作的真实备份目录，只读检查 `installation.json` 和被哈希绑定的文件：

```powershell
pwsh -File tools/restore-dsh.ps1 -BackupDirectory '<实际备份目录>' -CheckOnly
```

恢复器读取 v2 和 v3 收据。只有下列条件同时成立，才允许仅回滚 MCM 文件：保存的 profile 更新前后完全一致，旧版与新版依赖合同相同，当前包是真实指向标准目录的链接，而且备份及当前插件哈希符合收据。当前 profile 必须仍匹配收据；用户在安装后修改过配置时会拒绝，保留差异，不覆盖后来的设置。

如收据显示 profile 或依赖迁移，恢复以 `MCM_RESTORE_MIGRATION_REQUIRED` 拒绝，须先制定单独迁移恢复方案。恢复器**不调用全局 `install`，不求解或重装共享依赖**，也不通过改收据、关检查或强覆盖绕过限制。

预检通过后保存工作、正常退出 DSH，再执行：

```powershell
pwsh -File tools/restore-dsh.ps1 -BackupDirectory '<实际备份目录>'
```

恢复保留回滚前版本及独立恢复记录，暂存旧文件并核完整哈希，再切换标准目录，复核插件、profile 与实际链接。新旧副本保留也不意味着可以跨越后来发生的用户配置变化连续回滚。

v3 成功恢复记录 `status: restored_verified`、`restore_scope: plugin_files_only` 和 `dependency_install_performed: false`，仅证明收据约束及本次可核验范围内的 MCM 文件状态已恢复。启动后仍需检查版本、角色、原会话和其他插件。

v2 收据来自曾调用 CLI 的旧更新器；当时可能已改动 `node_modules`。即使满足上述可恢复条件，也只能证明插件文件、profile 与直接 manifest 等已检查状态；成功记为 `status: restored_plugin_files_verified`，并标注 `legacy_dependency_tree_unverified: true`，**不能宣称整个传递依赖树已恢复**。旧报告的验证范围保留，不因新工具支持读取旧收据而扩大。

## 失败处理与桌面启动诊断

升级或恢复失败时，以收据中的实际状态、错误和哈希为准，不因目录存在就报成功。保留旧版、新版、备份及失败现场；若自动恢复未完成，保持 DSH 关闭，按差异处理，不反复强覆盖。

本轮桌面真实启动问题已收敛到 browser userdata 状态；具体本机路径、截图和原始日志不进入公开材料。根锁文件审计异常是另一项依赖诊断，不能据此归因 Web 认证问题。维护工具的源码修复也不证明候选已经部署或桌面启动已由候选验证。
